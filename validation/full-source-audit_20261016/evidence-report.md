## Finding E1 — P2: Passing test summaries can turn a failed Cargo run into a passing receipt

Primary location: `design_docs/receipts/audio_foundation_20261011/ci/write-receipt.py:25-37`, especially 28-33. Related instance: `validation/font-roles_20261012/verify.py:31-37`.

The CI writer extracts only `test result: ok.` summaries. Consequently, every captured failed count is necessarily zero: a failed suite is printed as `test result: FAILED.` and is excluded before line 31 checks it. Line 33 then writes `exit_code: 0` rather than reading a captured command result. Metadata, lint, shell-syntax and whitespace exits at lines 55 and 80-83 are also literal assertions in the writer, rather than observations consumed by it.

**Concrete trigger:** a workspace log first contains all expected passing cases and then a later suite/doctest fails, or the wrapper fails after the expected summaries. A log with `test result: ok. 770 passed; 0 failed; 0 ignored` followed by `test result: FAILED. 0 passed; 1 failed; 0 ignored` still produces the expected `(770, 0)` tuple for Woodshed. Unless the failure contains the one specially rejected string `unexpected EOF`, the receipt writer accepts it and publishes a zero exit and zero failed tests. It also cannot distinguish a prior complete run's log from the intended invocation, because it consumes fixed filenames without a run/process identity.

The font verifier has the same filtering issue and checks only the final *matching successful* summary at lines 35-36. Appending a later failed summary to an otherwise valid 236-case core log leaves its acceptance predicate true. The build gate at line 37 checks a value already stored in `checks.json`; it does not establish the build process result from a process receipt. `--local` adds capture/binary/blob hashes but does not change these CPU predicates.

**Effect:** these helpers are unsuitable as fail-closed gates or independent rerun confirmation. A later failed suite or wrapper failure can be reported as successful, obscuring the distinction between passing cases and a successfully completed command. This is evidence-integrity impact, not a demonstrated runtime defect.

**Historical disposition:** the four actual CI rerun logs referenced by the writer sum to 770/148/253/157 successful cases (eight ignored in total); the inspected combined font logs contain 236 core, 161 view, and 159 host successful cases, with five nested child summaries correctly excluded from the 556 total. No historical failed suite was found in those logs. The finding is the retained acceptance logic, not a reclassification of these runs as failures.

**Smallest correction direction:** capture command exit status, start/end/run identity and exact command alongside the log when the command runs; require zero recorded process exit before counting cases; parse all suite outcomes and reject failed/error/truncated executions. Preserve intentional child-test deduplication explicitly. A receipt-assembly script should preserve historical facts instead of inventing missing exits. Add focused counterexamples for a later failed suite and post-test wrapper failure if these helpers are kept operational.

## Finding E2 — P2: The link-regression audit reads current targets for the historical baseline

Location: `validation/link-model-p6_20261016/doc_link_audit.py:17-40`, especially 21-22 and 30-36; subtraction/exit at 49-57.

`scan(..., revision=base)` obtains the referring document from `git show`, but checks target existence and headings using `target.exists()` and `target.read_text()` in the current filesystem. The baseline and current scans therefore resolve links against the same current target state.

**Concrete trigger:** a receiving document contains `[reference](#retained-heading)` at the base revision. The heading exists at base. A change deletes/renames that heading while retaining the link. During the baseline scan, the old link is checked against the newly changed document, so it is already recorded as broken. The current scan records the same broken link. The `Counter(current) - Counter(baseline)` subtraction at line 53 is empty and the script reports `no_new_findings: true` and exits zero. Deleting an existing linked target file has the same failure mode.

**Effect:** a new documentation regression is silently classified as baseline debt. The script cannot substantiate its claimed before/after link-regression result for target edits or deletions. The stored `doc-link-audit.json` packets for P6 and Stage P4f contain zero findings, but this source-only review did not reconstruct their historical Git trees, so it does not assert those particular packets concealed a broken link.

**Smallest correction direction:** resolve both referring documents and repository-local target bytes/existence from the same revision during the baseline scan; use current worktree targets only for the current scan. Handle same-document anchors through the already loaded revision-specific text. Keep matching/anchor-normalization improvements separate. Cover heading deletion and target-file deletion with focused fixtures.
